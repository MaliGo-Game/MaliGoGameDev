# Phase 1 completeness review

Gaps, contradictions and unsupported claims found across the six research reports. The design spec resolves each one.

## Gaps

1. END-OF-DAY DATA MODEL HAS NO SINGLE OWNER. systems-current-state §5 specifies DayRecord/MoneyEvent hooks; ui-ux-direction §5.6 and market-and-behaviour §5.4 each specify different reveal content. None of them defines the final schema: the pools to snapshot (cash, savings, goal pot, the proposed stokvel pot, arrears), the bucket labels (Transport/Food/Family/Bills/Pay-later, market B7), the 'Coming up' horizon, and the chapter-level aggregation for 'three moments that moved it most' (ui-ux §5.7). To resolve: DESIGN_SPEC needs one DayRecord/ChapterRecord schema plus the invariant start + Σdeltas == end for each pool, checked by a script outside Unity.

2. NOBODY HAS CHECKED THAT THE LOGIC CAN BE TESTED OUTSIDE UNITY (MASTER_PROMPT §7 'Pure logic gets scripted checks'). Assets/MaliGo/Data/FinancialStats.cs:2 and FinancialGoal.cs:2 import UnityEngine. ScenarioManager.AddRepayments uses Mathf (ScenarioManager.cs:191), as does HomeInteraction. None of the six reports says whether ObligationLedger, PlayerData and the proposed DayLedger can build under plain dotnet, or which Mathf shim the checks would need. market §8 and systems §5.3 both assume the checks will exist. To resolve: list the Unity dependencies of every logic file, then decide on a test harness (a dotnet console project linking those .cs files plus a Mathf stub).

3. THE BASELINE COMPILE STATE WAS NOT REPORTED. systems §4 and build-readiness §4 both say 'not verified'. Evidence that would partly settle it: %LOCALAPPDATA%/Unity/Editor/Editor.log (3 Oct 15:31) shows '*** Tundra build success (168.39 seconds)' with only CS8785 warnings, so the Editor compiled the working tree as it was today. To resolve: run the MASTER §7 csproj dotnet check once at 184fe73f before any build work, so later errors can be told apart from pre-existing ones.

4. THE WORLD SCENE HAS NO AUDIOLISTENER. Assets/Scenes/MaliGoWorld.unity has one Camera (!u!20) and zero AudioListener (!u!81) components. CharacterCreation.unity has one. Any ambience, Mali cue or UI click in the world scene would be silent. asset-manifest §5/§8 lists the clips; no report covers the audio architecture (listener, AudioSource pooling, a mixer or volume groups, persisting the sound and music toggles that ui-ux §5.9 puts in Pause, and switching ambience by zone such as the Johannesburg CBD clip 'for the taxi rank'). To resolve: an audio section in DESIGN_SPEC, and a runtime Step that adds an AudioListener to the main camera.

5. REPLACING THE HUD WITHOUT EDITING THE SCENE IS NOT PLANNED. The current HUD is baked into MaliGoWorld.unity (MaliGo_Canvas, HUD_StatusPanel, Goal_Panel; ui-current-state §3.2), and HUDController finds its labels by their text. ui-ux §5.1 specifies a new pill HUD. MASTER §7 says not to edit .unity files. No report says how the new HUD coexists with the scene canvas, for example disabling MaliGo_Canvas children at runtime from a bootstrap Step. Bootstrap.cs:81 and :99 also look objects up by name. To resolve: a spec decision to hide the scene HUD at runtime and build the new one in code, with a note that HUDController then gets retired.

6. THERE ARE NO SETTINGS OR FIRST-RUN PERSISTENCE MODEL. ui-ux §5.8/§5.9 needs firstRunStepsSeen, text speed, reduce motion, sound and music. market §5.5 needs a stored payday-plan sentence and amount, then quoted back in N7. No report says whether these live in PlayerData (and are therefore wiped by 'Start over…') or separately (build-readiness says PlayerPrefs is unused). To resolve: DESIGN_SPEC states which settings survive a reset save and where each one is stored.

7. SAVE MIGRATION FOR EXISTING TESTERS IS NOT PLANNED. A 64.2 MB APK from 22 Sep is already on disk and may be on testers' phones (build-readiness §1). Those saves have R5,000+ cash, the old goals and possibly all 8 scenarios completed. A new chapter/day schedule, a fixed R600 start (market F3) and a DayRecord (systems §5.3) all change the meaning of the save. Only TryLoad back-filling is mentioned (systems §5.3). To resolve: the spec decides between a save version field with forced reset and migration, and keeps the same package id and debug key so updates install (build-readiness §2).

8. THE ENERGY ECONOMY IS NEVER ANALYSED, yet MASTER §9 requires 'Energy visible'. Energy resets to 100 every night (HomeInteraction.cs:106). Work costs 20 and the largest scenario energy cost is -15 (ScenarioLibrary.cs:121). Market's day plan is 2-3 scenarios plus a shift, so energy can never bind, and an energy bar shows a number with no consequence. No report checks this. To resolve: the spec decides what energy gates (for example walking-option costs, or a second shift), or presents it as information only; the economy script from market §8 should include energy.

9. THE STRESS STAT'S ROLE AND VISIBILITY ARE UNDECIDED. ui-current-state §3.2 flags 'Financial Stress: n%' as a de facto score. ui-ux §2/§5.4 removes it from the HUD and choice cards. market's new scenarios (N1-N6) still use stress deltas everywhere. MaliContextualDialogueSelector uses stress ≥ 60 (systems §2.6), and ObligationLedger adds 10 stress for each missed night. To resolve: a spec decision on whether stress is hidden like the behaviour scores and only shapes Mali's lines, or is shown in words.

10. THE GOAL MODEL IS UNRESOLVED. CharacterCreationUI.cs:403-418 pre-fills a goal of R1,500-12,000 with a third money pool (systems R24). market §5.1 wants an R2,000 buffer for everyone. ui-ux mock-ups use a 'fridge goal'. The Bank 'Contribute R50 to goal' moves money out of cash and savings. Nobody says whether the goal pot remains, merges into savings, or becomes the 'buffer'. To resolve: the spec defines the goal (fixed or player-chosen, pooled or separate), and character creation is updated to match.

11. THE CHARACTER-CREATION FLOW HAS NOT BEEN RECONCILED WITH A FIXED CHAPTER 1. market F3 normalises the start money, and systems §4 says to lock or hide the life stages. ui-current-state §3.1 lists 8 financial-profile rows (risk tolerance, investing) that would then do nothing. No report proposes what character creation should ask in the beta, or where Mali appears in first-run (ui-current-state defect 7). To resolve: a first-run section in the spec that trims character creation to name, appearance and goal, and introduces Mali.

12. SCENARIO PACING HAS NOT BEEN CHECKED AGAINST WORLD GEOGRAPHY OR SESSION LENGTH. MASTER §5 asks for 'a decision every few minutes, never a dead world'. Nobody measured walking distances or times between Player_House, Local_Commercial_Hub, Road_Main_4 and Local_Bank_Building, or how long a day lasts. market §5.2 adds 6 more triggers at locations where systems R16 and ui-current-state §3.6 already find stacked prompts. To resolve: measure trigger positions in ScenarioWorldWiring and WorldLocationWiring, then assign each scenario a spot that doesn't overlap.

13. NEW SCENARIO LOGIC HAS NOT BEEN SCOPED INTO THE BUILD. market §5.3 needs a stokvel-pot bucket (N5, F8), conditional fees (N6), cash-conditional gating (N4), a dated calendar ('Mon 18th', payday on the 25th), free-text or Rand-adjustable plan input (§5.5), and Mali memory of yesterday (B10). systems §5.3 has hook points only for existing flows. To resolve: the spec marks each one as beta or later and gives each a data shape (a schedule asset with a day → scenario list that can be switched off, per MASTER §5 A/B).

14. THERE IS NO FEATURE-FLAG MECHANISM. MASTER §5 asks for features to be switchable so they can be compared against a default. market mentions it (§1.3, F10) but no report proposes where the flags live: a ScriptableObject, a static config, or bootstrap Step toggles. To resolve: a short spec section with one config class that Bootstrap reads.

15. THERE IS NO AUTHORING PLAN FOR MALI'S REFLECTION COPY. The reveal needs a generated line: the biggest mover, then what's next, then optionally the goal (market §5.4 rule 3, ui-ux §5.6 step 7). The chapter end needs 'What Mali noticed' built from the hidden behaviour tags (market §5.5). No report specifies the template system, how lines are chosen, the fallbacks, or how many lines need writing. MaliDialogueLibrary has only 8 entries (systems §2.6). To resolve: the spec defines the line templates and the selection rules, and lists the content to be written.

16. ICONS AND GLYPHS FOR THE PLANNED UI ARE NOT COVERED. ui-ux §5.1/§5.3 mock-ups use ☀ ϟ ▣ ▤ ▼ ✓ ✕ ‖ ↔ ▲ and U+2212/U+00A0. asset-manifest §4.1 found Aileron lacks U+00A0, ▼, ✓ and ✕, and has no energy, bank or calendar icon (§3.7). Nobody checked LegacyRuntime.ttf glyph coverage. To resolve: dump LegacyRuntime/Arial and Aileron cmaps with fontTools and replace every glyph that isn't covered with a sprite, listed in the spec.

17. THE MALI ART NEEDS PREPARATION THAT IS NOT ASSIGNED. Viewing Assets/Mali Dumbfound.png confirms the mirrored 'Я' on the coin (ui-ux §1.2). It also has a plant at the bottom right, an edge fragment on the left and roughly 200 px of empty space at the top, so it needs cropping. mali2.png (RN app) has to be copied in and approved. The app icon (build-readiness P0-3) and the portrait (ui-ux §5.3) both depend on it. To resolve: an asset-prep task list that names the founder approval, the crop sizes, and Resources placement (build-readiness §Resources baking).

18. REMOVING THE PACKAGE AND EDITING SETTINGS NEEDS THE EDITOR, AND NOBODY HAS ASSIGNED THAT. build-readiness P0-1 (remove com.unity.ai.inference, re-resolve packages-lock, delete the app-ui config line and the APP_UI_EDITOR_ONLY define), P1-9 (QualitySettings) and P1-10 (URP HDR) change Packages/ and ProjectSettings/, which the dotnet compile check cannot validate. To resolve: the spec marks these as founder-laptop or Editor steps run before the headless build, or moves them into MaliGoAndroidSetup.Configure() code.

19. THE BRANCH AND PR BASE ARE UNCONFIRMED IN THE REPORTS. MASTER §7 says to branch off sam/core-loop-u1-u3. I checked: agents/beta-finish does contain origin/sam/core-loop-u1-u3 (merge-base --is-ancestor succeeds). TEAM_TASKS.md, which the brief references, does not exist (systems §0 note). To resolve: note both points in DESIGN_SPEC so build agents don't go looking for TEAM_TASKS.md.

20. THE NOTION OKRs ARE STILL UNREAD (MASTER §10). No report mentions them, and they may change priorities. To resolve: the founder authorises the Notion connector before the spec is frozen.

## Contradictions

1. THE HEADLINE NUMBER OF THE REVEAL IS DEFINED THREE WAYS. systems-current-state §5.1 recommends cash + savings + goal pot. ui-ux-direction §0.6/§5.6 says cash + savings, with savings moves as neutral transfers, and ignores the goal pot (so 'Contribute R50 to goal' would read as a R50 loss). market-and-behaviour B7/N5/F8 adds a fourth, committed stokvel pot shown separately, and its mock-up (§5.4) has a separate 'Savings: R400 → R400' line. To resolve: one definition in DESIGN_SPEC that lists the pools, which moves count as transfers, and how committed money is shown.

2. THE CHOICE PANEL CONSEQUENCE TEXT CONFLICTS. market B1 says keep the free-text description ('Cash -R50, Stress -5', ScenarioLibrary.cs:71) as the capability cue. ui-ux §5.4 says stop showing description strings, generate Cash/Energy/Later columns from the deltas, and keep stress off. To resolve: adopt the ui-ux generated columns (they also stop the text drifting from the real deltas, as in the R13 redirect_to_savings bug) and note it against market B1.

3. THE FONT CHOICE CONFLICTS. ui-ux-direction §4.2 picks Nunito (OFL, needs founder approval) and specifies 'R1 250' with a U+00A0 group separator. asset-manifest §4.1 recommends Aileron (CC0) as the brand font and found that Aileron has no U+00A0, ▼, ✓ or ✕, so it says to format with a plain space or none. To resolve: the founder decides between OFL and CC0, then the money formatter and the glyph-or-sprite list are set to match the chosen font's measured cmap.

4. PROCEDURAL SURFACES CONFLICT WITH STAGED KENNEY PANELS. ui-ux §0.4/§6 says draw every surface procedurally and retire Kenney panels. asset-manifest §3.1/§8 shortlists eight Kenney UI Pack 2.0 panel and button PNGs for Assets/MaliGo/UI/Panels, then hedges 'or skip if the procedural UiKit lands first'. To resolve: pick one in the spec (procedural is recommended) and drop the panel imports so no unused assets enter Assets/.

5. THE REVEAL'S USE OF COLOUR AND GLYPHS CONFLICTS. market §5.4 says no colours meaning good or bad, no ticks or crosses, +/- signs only, and its mock-up uses an all-caps header 'TUESDAY, 19TH'. ui-ux §4.1/§5.6 uses ▲ ▼ ↔ glyphs, money.in green and money.out brown colour tokens, and 'sentence case everywhere, no all-caps'. To resolve: the spec picks one; the ui-ux tokens with neutral brown work if the glyphs are confirmed to render.

6. THE HUD CONTENT CONFLICTS. market §5.1/B12 wants 'Mon 18th · Day 1 of 7 · Payday in 7 days'. ui-ux §5.1 wants Day, Cash, Savings, Energy, Next bill and Pause, with no chapter length or payday. ui-current-state §3.2 and ui-ux both drop Level and XP, while market B1 wants the player's goal in Rand on the HUD (ui-ux puts the goal only in the chapter end). To resolve: one HUD element list in the spec.

7. THE UI-UX MOCK-UP NUMBERS CONTRADICT THE CODE AND THE PROPOSED CHAPTER. The mock-ups show 'Shift at the shop +R350', 'Rent R1 200', 'Phone R99 on Day 6', 'Payday's in 4 days', and an 'Eat at home −R20' action and Bank 'R200 · All' chips. The code pays R150 per shift (WorkInteraction), rent is R500 a week and airtime R60 a week (ObligationDefaults.cs:16-17), no phone bill, Home action or R200 Bank action exists, and there is no payday concept. market §5.1 starts with R600. To resolve: rebuild the spec mock-ups from the real or agreed chapter numbers so builders don't copy illustrative values.

8. THE BILL TIMING IS OFF BY ONE BETWEEN REPORTS. market §5.1/§5.2 says airtime settles 'on the night of Day 2' and rent 'on the night of Day 3'. The code sets nextDueDay = today+1 and today+2 (ObligationDefaults.cs:24-25, 41, 50). SleepAndEndDay increments currentDay before SettleDue (HomeInteraction.cs:104-105), so airtime is charged when sleeping at the end of Day 1 and rent at the end of Day 2 (systems §2.4 is consistent with the code). The 'Due tonight' copy in ui-ux §5.5 also depends on this. To resolve: the spec defines 'due day N' as paid on the night that ends day N-1 or day N, and the code and the market day table are aligned to it.

9. THE SAFE-AREA APPROACH CONFLICTS. build-readiness P1-11 says set androidRenderOutsideSafeArea to 0, which 'keeps all UI clear of notches without touching the runtime UI code'. ui-ux §3/§5.0 and systems R7 say add a SafeAreaFitter on every canvas, and ui-ux notes Android 15+ edge-to-edge. The installed SDKs are android-36 and android-36.1 (Sdk/platforms), so with target SDK Auto the app targets API 36, and the build-readiness shortcut may not hold. Build-readiness P1-12 (AutoRotation between both landscape sides) also means the cutout switches sides at runtime. To resolve: implement a SafeAreaFitter that updates on Screen.safeArea change, regardless of the setting, and test it in the Device Simulator.

10. THE CANVAS-UNIT TO DP CONVERSION DIFFERS. ui-current-state §1 uses Android density buckets: phone B, 1600x720 at 2.0, comes out at 0.333 dp per unit under height-match, so 48 dp needs about 144 units. ui-ux §2 uses physical ppi/160 and says 1 unit is about 0.40 dp on every phone, so 120 units = 48 dp. Android reports bucketed density, so under ui-current-state's assumption a 120-unit target is about 40 dp on a budget 720p phone, below the brief's 48 dp. To resolve: size targets from the worst-case bucket (about 144 units at height-match) or measure on the test phone.

11. THE DIALOGUE-OVER-CONTROLS OVERLAP CLAIMS DIFFER. ui-ux §2 says the mobile controls (sort 25) draw over Mali's box (sort 20). ui-current-state §3.7 computed that the rectangles don't overlap at 20:9 or 16:9 today. Both agree that enlarged panels will collide. To resolve: no action on the current UI, but the spec's sort orders (ui-ux §5.0) and the rule that controls dim during dialogue should be adopted explicitly.

12. THE SCENE FOR THE CHAPTER-END ART IS NAMED INCONSISTENTLY. ui-current-state §5 lists Assets/MaliGo Pitch Deck.png as 'size —, unused'. ui-ux §1.2/§5.7 identifies it as Mali waving full-body, 779x779 with alpha, and uses it on the chapter-end screen. Viewing the file confirms a clean full-body wave. This is only a naming risk: the filename contains 'Pitch Deck'. To resolve: rename it on import (for example MaliWave.png) so no pitch-deck naming ships.

13. SAVE CADENCE: build-readiness §2 and §7 say it 'couldn't check how often Save() is called'. systems-current-state §2.2 lists every saveImmediately call site, the answer being after every mutation. Both still recommend OnApplicationPause. To resolve: there is no real conflict; the spec should cite systems §2.2.

## Unsupported claims

1. Many file:line references in ui-current-state.md point past the end of the file and cannot be correct. Examples: EventSystemUtility.cs:245-265 (the file has 38 lines); MobileControlsUI.cs:290-355, :302 and :353 (220 lines; the scaler is at :103 and 'ACT' at :154); HomeInteraction.cs:248-368 (145 lines; SleepAndEndDay is at :95); BankInteraction.cs:390-425 (142 lines); WorkInteraction.cs:530-532 (87 lines); ActionPanelUI.cs:291-328 (248 lines); ScenarioTrigger.cs:302-347 (191 lines). Builders should treat that report's line numbers as approximate and use systems-current-state's, which match the code. Some ui-current-state refs do check out: ScenarioChoiceUI.cs:54/:140, HUDController.cs:173.

2. market-and-behaviour §1.1 says the 27 PDFs 'are also copied untracked into docs/research/'. docs/research contains only the six .md reports. The 27 PDFs are tracked in git under 'Behavioural Research/' (git ls-files shows 27).

3. market-and-behaviour §5.1/§5.2: the bill-night timing (airtime on Day 2 night, rent on Day 3 night) conflicts with the code, which pays them on the Day 1 and Day 2 nights (see contradictions). The §5.2 'rough economy check' (tight path ends at about R1,000 cash) is hand arithmetic that the author also says was never scripted.

4. market-and-behaviour §5.2 says 'Saturday has no shift pressure'. The code allows one shift every day with no weekday concept (WorkInteraction uses lastWorkedDay only).

5. ui-ux-direction §0.2/§4 says 'about 0.40 dp per unit on every phone' at match=1. This rests on physical ppi, not Android's bucketed density, and is not verified on hardware (the report's §8 hedges ±10%; the budget-phone gap is about 17%).

6. ui-ux-direction §3 says target SDK 'very likely ≥ 35'. This was not checked by that agent; it is confirmed here (android-36 installed). The consequence, that edge-to-edge is enforced, is still not verified for Unity 6000.3's player.

7. build-readiness §1/§3 P0-1 says the AI package is 'the most likely reason the builds are so slow' and that the APK will be 'well below 64 MB'. Both are estimates with no measurement. The Personal-licence splash removal (P1-8) is also unverified.

8. build-readiness P1-11 says renderOutsideSafeArea=0 'keeps all UI clear of notches' on its own. That is unverified on API 36 edge-to-edge and with landscape auto-rotation.

9. asset-manifest §5 audio role picks (glass_001 as the Mali cue, the STEEL01 chime as 'warm', loopability of the Freesound beds) are based on filenames only; nothing was auditioned, as the report says. The claim that legacy UnityEngine.UI.Text accepts OTF as a dynamic font is untested in this project. The 9-slice borders are estimates.

10. asset-manifest §3.2-3.4 icon file names (for example shoppingBasket.png, pouch_add.png, timer_CW_25.png) come from staged folders outside the repo (C:\Temp\MaliGoAssetsStaging). No other report checked that those folders exist or that the files render at 48 dp.

11. market-and-behaviour statistics rest on press write-ups or vendor and sponsored sources the report itself flags: OMSIM 2026 via FA News/BusinessDay, the Floatpays '76%', Vault22 '68% black tax', the Standard Bank R130 fee from a search summary, mashonisa 30-50%. The anti-streak rule's evidence is partly weak-method (Celestin & Vanitha). These are fine for direction, but none should appear as player-facing 'facts'.

12. ui-ux-direction §3: the Material 3 motion values and the Papers, Please / Stardew screen descriptions come from search summaries or memory (pages returned 402 or did not render), as the report admits.

13. systems-current-state R1 (ACT contention decided by Update order), R10 (joystick stuck after pause) and R11 (emoji tofu) are inferred from code and labelled 'plausible'. ui-current-state's text-width overflow findings assume LegacyRuntime.ttf matches Windows Arial metrics and a line height of about 1.15. None was run in the Editor or on a phone.

14. ui-current-state §3.2 says the HUD canvas is 'generated by Editor/MaliGoWorldGenerator.cs:497-585 / MaliGoSceneSetup.cs:139-242'. Given that report's systematic line-number drift, these ranges were not cross-checked and should be re-verified before anyone relies on them.
